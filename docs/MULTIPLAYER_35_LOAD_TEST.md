# Eco Chronicle 35명 멀티플레이 부하 시험

시험일: 2026-09-24. Windows 로컬 프로젝트의 정적 HTTP 서버와 Codex 인앱 브라우저에서 실행했다. 실제 접속 시험은 운영 Supabase Realtime의 테마별 `eco-forest`/`eco-river` 채널을 사용했다. 35명 시험은 한 브라우저의 실제 `ecoRemotePlayers.sync()`, `receivePosition()`, `refresh()`, `ecoOnlinePlayers.update()`/모달 DOM 경로에 가상 사용자 34명을 주입했다. 별도의 Node 시험은 실제 `presence.js`를 가짜 채널에 연결해 35명 파싱, 재접속 및 20회 테마 전환을 확인했다. **35개의 실제 브라우저 또는 Supabase 소켓을 열어 보지는 않았다.**

## 시험 범위와 결과

| 항목 | 결과 |
| --- | --- |
| 실제 동시 접속 | 수정 전 5개 탭, 최소 수정 후 3개 탭 |
| 최대 모의 Presence | 35명, 중복 ID와 다른 테마 항목을 걸러 35명 유지 |
| 화면의 원격 캐릭터 | 자신 제외 34개 레코드와 DOM 요소 34개 |
| 접속자 목록 | 35행, 자기 자신 우선, 레벨 내림차순 확인 |
| 10명 퇴장/재입장 | 원격 요소 34→24→34개, 남은 플레이어 유지 |
| 이동 수신 | 34명이 2초 동안 125ms마다 보낸 544개 메시지 모두 적용; 절반 이동 시험 17명 × 8회 = 136개 적용 |

| 실제 퇴장·테마 이동 | 5탭 시험에서 B의 강 이동 및 E 탭 종료 후 숲 목록에서 각각 제거 |
| 실제 재접속 | D의 Realtime socket 강제 종료 후 로컬 이동 정상, 페이지 재로드 후 숲 Presence 3명으로 복구 |

실제 5개 탭에서 A/B/C/D/E가 모두 숲에 표시됐고 네 원격 캐릭터가 각 화면에 생성됐다. 서로 다른 방향으로 동시에 이동할 때 원격 좌표와 방향이 갱신됐다. 최소 수정 후 다시 연결한 A/B/C 세 탭에서도 3명 Presence, 원격 캐릭터 2개씩, B 이동의 A 화면 반영을 확인했다. 이 3개 탭의 브라우저 오류·경고는 각각 0개였다.

5탭 시험 초기에 직전에 닫은 별도 시험 탭의 `여행자-…` Presence가 일시적으로 여섯 번째 접속자로 보였다가 제거됐다. 이후 5명으로 수렴했고, E 탭 종료 및 B의 강 이동도 숲 목록에서 제거됐다. 따라서 정상 수렴 후 영구 ghost는 관찰되지 않았지만, 탭 종료 직후 제거를 **항상 즉시** 보장한다고 해석해서는 안 된다.

## Broadcast 규모 계산

`js/movement.js`의 간격은 125ms이므로 움직이는 플레이어 1명의 위치 송신 상한은 약 **8회/초**다. 실제 코드는 좌표·방향·이동 상태가 같으면 송신하지 않고, 송신 중인 요청도 중복 실행하지 않는다. 테스트의 정지 구간에서 위치 Broadcast는 **0회**였다. 접속 직후 초기 위치, 이동 종료 1회, 새 멤버의 위치 요청과 이에 대한 응답은 일시적으로 추가될 수 있다. 위치 요청 재시도는 클라이언트별 최대 3회다.

35명 전원이 계속 이동하는 상한은 채널에 **280개 송신/초**(35×8), 각 클라이언트에 다른 34명의 위치 **272개 수신/초**(34×8)이다. Supabase가 보낸 사람을 제외한 모두에게 각 이벤트를 전달하면 전체 수신 전달은 약 **9,520개/초**(35×34×8), 송신과 수신 처리의 합은 약 **9,800건/초**다. 이는 코드의 간격으로 계산한 상한이며, 실제 35개 소켓의 서비스 처리량이나 네트워크 사용량을 실측한 값은 아니다. 17명만 이동하면 송신은 약 136개/초다. 요약 정보는 movement Broadcast에 섞이지 않고 변경 때에만 Presence `track()`이 실행됐다. 변경 없는 상태로 Presence 점검을 20회 돌려 추가 `track()` 0회를 확인했다.

## 렌더링·DOM 측정

데스크톱 크기 1280×720, 단독 시험 탭에서 34명이 125ms마다 움직이는 2초 구간의 평균은 **59.9FPS**, 프레임 간격 p95 **17.2ms**, p99 **17.4ms**, 50ms 초과 프레임 **0개**였다. 544개 위치 처리에 누적 약 **1.6ms**가 들었다. 35명 접속자 표의 연속 35회 갱신은 회당 평균 **0.37ms**, p95 **0.5ms**, 최대 **0.5ms**였다.

35명 표시 전후 DOM 노드는 **876→1,115개**였다. 즉시 20회 테마 전환의 직전/직후는 **1,114→1,114개**, 간격을 둔 20회 뒤 **1,115개**, 전원 제거 뒤 **877개**였다. 원격 레코드와 원격 DOM 요소는 제거 뒤 모두 0개였다. 노드 수가 단조 증가하는 구조적 누수는 관찰되지 않았다. 브라우저의 정확한 JavaScript heap/GC 수치는 확보하지 못했으므로 장시간 메모리 사용량까지 보증하지는 않는다.

정지한 원격 캐릭터는 기존 500ms 점검 때 불필요한 단일 애니메이션 프레임이 약 2회/초 예약됐다. 최소 수정 뒤 2.5초 정지 시험에서 원격 애니메이션 예약은 **5→0회**, 이동이 수렴한 뒤 1초에도 **0회**였다. 이름 텍스트도 바뀌었을 때만 다시 쓴다. 이동 구간 평균 FPS는 수정 전후 모두 **59.9**였다. 변경은 원격 렌더러의 정지 판정과 동일 문자열 확인 두 곳에만 적용했다.

390×844 화면에서 접속자 35행을 실제 표시했다. 목록의 세로 스크롤 높이는 약 **1,152px**, 보이는 높이는 약 **373px**이며 패널은 화면 안에 있었다. 헤더는 `sticky`였고, 표에 가로 스크롤을 적용해 **267px** 가시 폭에서 **450px** 너비의 모든 열을 탐색할 수 있었다. 수정 전에는 레벨도 잘렸지만 수정 후 `Lv. 35`를 읽을 수 있었다. 긴 닉네임·장비·단계는 말줄임 처리된다.

전체 자동 시나리오에는 20번의 테마 왕복을 **한 JavaScript 작업에서 즉시** 실행하는 인위적인 구간도 넣었다. 이 구간은 약 **524ms**가 걸렸고 약 **552ms** 장시간 작업 1개를 유발했다. 그 때문에 전체 시험 평균 FPS는 약 51.5, p99 프레임 간격은 약 116.7ms로 이동 구간 수치보다 낮다. 간격을 둔 20회 왕복은 한 번에 최대 약 **27.4ms**였고, 인원·DOM 수는 증가하지 않았다. 이 병목은 매 테마 입장 때 원격 요소 34개를 다시 만드는 비용이다. 사용자가 수십 번을 한 틱에 왕복하는 상황은 실제 UI에서 발생하지 않으므로 게임 구조를 바꾸지 않았다.

## 실패·회귀·한계

- CDN 미로드 시험에서는 Supabase 연결 오류 로그가 예상대로 나왔지만 로컬 이동, 가방, 지도, 저장과 이어하기, 일반 전투 화면, 팡팡 미니게임 화면에 진입할 수 있었다. 전투·미니게임 진입은 로컬 시험 페이지에서 기존 검증용 함수(`admFight`, `admMini`)를 호출했으며 게임 로직은 변경하지 않았다.
- 실제 Realtime socket을 끊은 탭에서는 원격 캐릭터가 비워지고 로컬 이동이 계속됐다. 페이지 재로드로 재접속을 확인했다. SDK의 **자동** 재접속은 이 실제 시험에서 확정하지 못했다. 가짜 채널의 `CHANNEL_ERROR`→`SUBSCRIBED` 전환 시험에서는 Presence 재등록과 목록 복구가 통과했다.
- 연결된 3개 실제 탭의 JavaScript 오류 0개, 경고 0개였다. 실패 시험의 `Supabase CDN unavailable` 오류와 가짜 채널의 예상 `CHANNEL_ERROR` 경고 1개는 의도된 장애 신호이며 치명적 오류는 없었다.
- 원격 패킷 순서, 멤버 검증, 유휴 전송 억제, 8Hz 상한, 로컬 상태 분리는 기존 `tests/movement.test.cjs`에서도 통과했다. 오래된 채널의 콜백은 `presence35.test.cjs`에서 무시됨을 확인했다.

## 기술적 판단과 변경 파일

**클라이언트 렌더링은 이 환경에서 35명 규모를 감당했다.** 다만 35개 실제 기기의 동시 연결, 무선망 혼잡, Supabase 서비스의 실제 fan-out/요금·한도는 시험하지 않았다. 따라서 교실 전체에 바로 안정성을 보증하기보다 **조건부 사용 가능**으로 판단한다. 실제 수업 전에는 목표 네트워크에서 35개 소켓으로 280 송신/초·최대 9,520 수신 전달/초를 확인해야 한다.

제품 파일 변경은 `js/remote-players.js`의 유휴 렌더링 억제와 `css/online-players.css`의 좁은 화면 표 가로 스크롤뿐이다. 시험용 `tests/serve-movement.cjs`, `tests/movement.test.cjs`를 수정하고 `tests/load35-browser.js`, `tests/presence35.test.cjs`를 추가했다. Presence, Broadcast, 저장 및 게임 로직은 변경하지 않았다.
