# 월드 이동 Broadcast 구현 및 검증

검증일: 2026-09-24. 범위: 같은 테마의 표시 전용 원격 캐릭터 이동과 방향.

## 변경 파일

- 신규 `js/movement.js`: 월드 상태 읽기, 전송 제한, Broadcast 수신·초기 위치 요청·통계.
- 수정 `js/presence.js`: 기존 채널에 이동 처리 연결, 멤버십 전달, 연결/퇴장 수명 관리.
- 수정 `js/remote-players.js`: 좌표 검증, 개인별 target/sequence, 보간·스냅, 기존 걷기 렌더링 재사용.
- 수정 `index.html`: Presence 앞에 movement.js 한 줄 추가.
- 신규 `tests/movement.test.cjs`: 의존성 없는 자동 검사.
- 신규 `tests/serve-movement.cjs`: 로컬 브라우저 검증 서버. 응답 HTML에만 테스트 입력/진단을 추가한다.
- 신규 `docs/MOVEMENT_SYNC_TEST.md`: 이 보고서.

`js/game.js`, CSS, Supabase 초기화 파일, 저장 구조/키, 전투·미니게임 코드는 이번 단계에서 수정하지 않았다. 앞 단계 파일들이 아직 Git 미추적 상태이므로 전체 Git 상태와 이번 단계의 변경 목록은 다를 수 있다. 커밋·푸시는 하지 않았다.

## 채널과 전송 규칙

기존 `eco-forest`, `eco-river` 등 Presence 채널 **하나를 그대로 재사용**한다. 추가 이동 채널은 없다. `broadcast.self=false`이며 수신 측에서도 자신의 ID를 거부한다. [Supabase 공식 Broadcast API](https://supabase.com/docs/guides/realtime/broadcast)의 channel.on/send를 사용한다.

`world-position` payload:

```js
{ playerId, theme, joinedAt, seq, x, y, direction, moving }
```

joinedAt은 기존 Presence의 채널 입장 식별값이다. 같은 ID가 나갔다 돌아온 경우 이전 입장의 지연 패킷을 거부하기 위해 함께 보낸다. seq는 페이지 수명 동안 단조 증가한다. 레벨·장비·HP·경험치·골드·전투·퀘스트 데이터는 없다.

- 기본 주기 **125ms, 최대 약 8회/초**. 별도 타이머가 기존 Wd.px/py/face/moving을 읽는다. 좌표는 소수점 한 자리로 전송한다.
- 좌표·방향·moving 변화, 최초 입장, 새 참가자 초기 위치 응답에만 전송한다. 같은 상태를 주기적으로 반복하지 않는다.
- 새 참가자는 `world-position-request`로 정지 중인 기존 참가자의 위치를 요청한다. 이 요청에는 playerId/theme/joinedAt만 있으며, Presence 확인 전 패킷 손실에 대비한 초기 요청은 750ms 간격으로 최대 3회다. 응답도 125ms 타이머에 합쳐 전송한다.
- 구독 및 자신의 Presence 확인 후 전송한다. 전송 중에는 새 요청을 쌓지 않고 다음 주기에 최신 상태를 읽는다. 실패 시 2초 뒤 재시도하며 경고는 10초에 한 번으로 제한한다.
- 기존 키 입력/로컬 이동은 수정하지 않았으며 네트워크 응답을 기다리지 않는다.
- 개인 화면으로 전환될 때 한 번 정지 상태를 보낸다. 월드 모달 진입 시 마지막 월드 좌표를 포착하고, 이후 개인 화면의 변화는 전송하지 않는다.

## 원격 렌더링

`ecoRemotePlayers.remotePlayers[playerId]`의 position과 별도로 targetX/targetY, lastSeq, networkMoving, animationState를 관리한다. Presence에 없는 ID, 자신, 다른 테마/입장, 이전 seq, 중복 seq, 잘못된 방향·숫자·맵 밖 좌표를 거부한다. Broadcast는 캐릭터를 생성하지 않는다.

렌더링은 requestAnimationFrame에서 `alpha = 1 - exp(-dt / 65)`로 목표에 접근한다. 프레임 간격은 최대 100ms로 제한한다. 목표와의 차이가 0.4px 미만이면 목표에 맞추며, 첫 패킷 또는 거리 차이가 **240px 초과**이면 즉시 스냅한다. 정착하면 연속 프레임 루프를 멈춘다.

기존 north/south/east/west 방향, head/body 스프라이트와 팔레트를 유지한다. `syncStride()`를 원격 전용 animationState로 호출하여 기존 9프레임 몸통 걷기와 보폭 표현을 재사용한다. 로컬 Wd나 S에는 쓰지 않는다. 충돌/NPC/몬스터 배열에 등록하지 않으며 저장에도 포함하지 않는다.

## 실제 브라우저 테스트

실제 Supabase 서비스와 로컬 HTTP 게임을 연결해 독립 탭 A/B/C를 동시에 실행했다. 초기 외형·Lv.5·forest 진입은 테스트 응답에서만 설정했다. 테스트 코드는 제품 index.html에 들어가지 않는다. 별도 localhost 포트와 EC9001~EC9003을 사용했다.

동시 지속 입력은 테스트 버튼으로 기존 이동 키 상태를 설정했다. 백그라운드 탭의 프레임 중단에 대비해 테스트 도구만 hidden 상태에서 기존 tick을 진행하도록 구성했다. 일반 키보드 입력도 별도로 확인했다. 원격 메시지나 원격 좌표를 테스트 도구가 대신 생성하지는 않는다.

| 항목 | 결과 |
|---|---|
| A/B/C forest 입장 | 각각 원격 2명, 로컬 hero 1개 |
| A 개별 이동 | B/C 모두 A 좌표·동쪽 방향 반영 |
| B 개별 이동 | A/C 모두 B 좌표·북쪽 방향 반영 |
| C 개별 이동 | A/B 모두 C 좌표·남쪽 방향 반영 |
| 3명 동시 이동 | 모든 탭에서 자신의 이동 중 나머지 2명의 moving=true 수신 기록 확인 |
| 정지 및 보간 완료 | 세 탭 모두 최종 목표 좌표 일치, moving/walking=false |
| 방향 변경 | 동/서/남/북 방향 데이터, 스프라이트 방향 및 걷기 상태 반영 |
| B river 이동 | A에는 C만, C에는 A만; B에는 forest 캐릭터 없음 |
| B forest 복귀 | A/C에 B 다시 생성, 최신 시작 좌표 (298,875) 적용 |
| C 탭 종료 | A에는 B만, B에는 A만 유지 |
| 가방·지도 | 열기/닫기/월드 복귀 정상; 가방 중 원격 레이어 숨김 |
| 저장·불러오기 | 저장 완료 후 초기화 주입 없는 시작 페이지에서 EC9001 이어하기 정상 |
| 기존 데이터 유지 | 플레이어A, Lv.5, HP 60/100, 골드 60 유지 |
| 정상 연결 오류 | 정상 접속 3개 탭의 JavaScript error/warn 0개 |

최종 2초 동시 이동의 정착 좌표:

| 캐릭터 | 로컬 좌표 | 다른 두 화면의 좌표 |
|---|---|---|
| A | (678.399,875) | (678.4,875) |
| B | (790.399,875) | (790.4,875) |
| C | (675.226,763) | (675.2,763) |

세 탭에서 동시 moving 상태가 겹치는 시점의 기록을 확보했다. 초기 위치 교환을 포함한 누적 위치 전송은 A 20회/B 21회/C 21회였고, 이후 정지 상태의 후속 확인에서도 동일했다. 실패 횟수는 0이었다. 초기 Presence 전에 받은 패킷 일부는 설계대로 무시됐고 초기 위치 요청으로 회복됐다.

안정화된 구간의 프레임 간격 95백분위는 세 탭 모두 약 **16.8ms**였다. 초기 이미지 로딩·백그라운드 전환은 별도이며, 모든 기기에서의 60fps 보장을 뜻하지 않는다. 원격 보간 중 실제 좌표가 목표 사이에 위치하는 것도 확인했다.

## 실패 및 자동 검사

- CDN 스크립트를 테스트 응답에서만 제외: 기존 Supabase 초기화 오류 안내, 원격 0명, 로컬 키보드 이동 x298→311 정상.
- 연결 후 Realtime socket을 테스트 버튼으로 끊음: `[Presence] CHANNEL_ERROR ... socket closed` 경고와 원격 표시 초기화, 로컬 키보드 이동 x298→314 정상. 정상 연결 중의 JavaScript 오류와 구분했다.
- `node tests/movement.test.cjs` 통과: seq 101 뒤 100/101 거부, 자신/다른 테마/미등록 ID/이전 입장/잘못된 좌표 거부, 제거 후 지연 메시지 부활 방지, 최초/큰 거리 스냅, 작은 거리 보간, 정지, 10명 독립 target/seq, 5초 정지 전송 0회, 모의 1초 이동 8회, 개인 화면 전송 억제, 실패 재시도 간격, 저장 상태 불변, 이전 채널 콜백 무시.
- 10명 검사는 가상 DOM 자동 검사다. 실제 10개 브라우저 성능 테스트는 수행하지 않았다.
- JavaScript 구문 검사와 `git diff --check` 통과.

발견한 제품 동작 문제는 개인 화면 진입 순간 마지막 이동분이 전송 주기 사이에 남는 경우였다. 모달 진입 시 최종 월드 위치를 한 번 포착하도록 수정하고 회귀 검사를 추가했다. 실제 재검증에서도 A 이동 중 가방 진입 후 로컬 x348.711과 B 화면의 A x348.7이 일치하고 moving/walking=false임을 확인했다. 테스트 서버의 초기 Windows 경로 비교와 진단 패널 너비 문제도 테스트 도구 안에서 해결했다.

전체 전투/보스/미니게임 완주 회귀 검사는 이번에 수행하지 않았다. 해당 소스는 그대로이며, 개인 화면의 상태를 전송하지 않는 정책을 자동 검사했다. 탭 강제 종료/네트워크 단절의 원격 제거는 Presence 서버가 감지하는 시점에 따르므로 즉시 0ms를 보장하지 않는다.

## 디버그와 다음 단계

콘솔에서 `ecoMovement.getStats()`로 intervalMs, onlineRemotePlayers, sent, received, ignored, requests, failures를 조회할 수 있다. 평상시 패킷별 로그는 출력하지 않는다.

다음 단계에서는 기존 playerId별 레코드, Presence 멤버십/입장 검증, 외형 렌더링을 재사용할 수 있다. 레벨·장비·진행도 표시는 이동 패킷에 섞지 않고 별도 허용 필드와 갱신 정책부터 정하면 된다. 이번에는 해당 공유, DB 저장, Auth, 전투 동기화를 추가하지 않았다.
