# 교실 사용을 위한 멀티플레이 안전장치 검증

## 범위와 환경

- 대상: 같은 테마 총 35명, 한 화면의 원격 캐릭터 최대 34명.
- 실행: 로컬 정적 웹 서버의 데스크톱 브라우저, CDN을 제외한 오프라인 고장 모드, Node 모의 Presence/Broadcast 테스트.
- 이전 실제 Supabase 다중 탭 검증은 `MULTIPLAYER_35_LOAD_TEST.md`에 기록되어 있다. 이번 변경 후 Galaxy Tab S5e 35대와 학교 Wi-Fi의 실제 동시 접속은 검증하지 못했다.
- 게임 상태, 저장 키, 전투 및 미니게임 로직은 변경하지 않았다.

## 적용한 보호 장치

| 상황 | 동작 |
| --- | --- |
| 정상 | 위치 변화가 있을 때만 125ms 간격(최대 약 8회/초)으로 Broadcast 전송 |
| 원격 인원 25명 이상 | 해당 페이지에서 전송 타이머를 하나만 유지하며 200ms(최대 약 5회/초)로 완화 |
| 10초 간격의 짧은 프레임 표본 두 번에서 각각 40ms 초과 프레임 8개 이상 | 200ms로 완화 |
| 전송이 600ms 초과한 경우 2회 연속 또는 전송 오류 2회 | 200ms로 완화; 응답이 4초를 넘으면 실패로 처리하고 재시도 간격 적용 |
| 위치와 방향, 이동 상태가 변하지 않음 | 위치 Broadcast 없음. 저부하 모드도 같은 정책 |
| 채널 오류·시간 초과·종료 | 원격 캐릭터와 접속자 목록을 비우고, 최대 3초간 SDK 재연결을 기다린 뒤 필요할 때 기존 채널을 제거하고 하나만 다시 생성 |
| 브라우저 오프라인 | 멀티플레이 표시를 비우고 오프라인 상태를 표시. 온라인 복귀 시 Presence 재등록 |
| 수동 비상 정지 | `window.ecoMultiplayer.disable()`로 Presence/Broadcast와 원격 표시 중지. `enable()`로 재시작 |

저부하 모드는 그 페이지에서 한번 켜지면 유지된다. 흔들리는 공용 Wi-Fi에서 전송 속도가 반복해서 오르내리지 않게 하기 위한 보수적 정책이다. 로컬 이동은 기존 게임 루프에서 계속 즉시 처리하며, Realtime 응답을 기다리지 않는다. 화면 밖 원격 캐릭터는 목표 위치로 바로 갱신하고 걷기 보간을 반복하지 않는다. 정지한 원격 캐릭터는 이미 애니메이션 루프를 유지하지 않았으며, 닉네임 DOM도 값이 달라질 때만 쓴다. 접속자 표는 요약 데이터가 달라질 때만 다시 그린다.

35명이 동시에 계속 이동하는 경우 저부하 모드의 계산상 전송 상한은 전체 약 175회/초, 각 기기의 다른 34명 위치 수신 상한은 약 170회/초다. 이는 이론상 상한이며 실제 학교망의 손실·지연·Supabase 제한을 측정한 값이 아니다.

## 비상 조작과 통계

브라우저 콘솔에서 `window.ecoMultiplayer.disable()`을 실행하면 온라인 부분만 멈춘다. 연결이 회복되면 `window.ecoMultiplayer.enable()`로 다시 켤 수 있다. `window.ecoMultiplayer.getStats()`는 `theme`, `onlinePlayers`, `remotePlayers`, `movementIntervalMs`, `sent`, `received`, `ignored`, `failures`, `reconnectCount`, `status`를 반환한다. 화면 오른쪽의 기존 접속 디버그 표시는 연결됨·연결 불안정·재연결 중·오프라인 모드를 작은 문구로 보여준다.

이번 검증은 기능 분리와 장애 후 정리 동작을 확인했다. 실기기 35대와 학교 공용 Wi-Fi에서의 프레임·지연·접속 안정성은 측정하지 못했으므로 실제 교실 사용 가능성을 확정할 수 없다. 현장에서는 먼저 한 반의 소수 기기로 접속과 비상 스위치를 확인하고, 문제가 생기면 멀티플레이만 끈 채 개인 게임을 계속 진행할 수 있다.
