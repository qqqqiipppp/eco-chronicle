# 기존 학생 저장 호환성과 배포 캐시 검증

2026-10-07 로컬 검증. 저장 구조 버전은 **9**, 배포 버전은 **2026.10.07.4**입니다. commit/push 및 실제 GitHub Pages 배포는 수행하지 않았습니다.

## 확인한 원인

- 기존 `v:8`은 초기 버전부터 계속 사용됐고, `migrate()`는 버전을 비교하지 않고 얕은 기본값만 추가했습니다. 탑·농장·학습·지역 진행의 중첩 누락은 보완되지 않았습니다.
- 저장을 읽기 전에 임시 쓰기를 요구하여 저장 공간이 가득 찬 경우 정상 슬롯도 읽을 수 없었습니다. 누락된 물 보충값은 로드할 학생이 아닌 이전 전역 학생의 물통 등급에 의존했습니다.
- 미등록 장비/기술 ID와 추가 퀘스트 필드를 기존 보정이 삭제했습니다. 이를 보존하도록 변경했습니다. 미등록 재료가 있는 브라우저 테스트에서 가방 표시 오류가 발견되어, 재료 데이터는 유지하고 현재 지역에서 정의된 재료만 표시/판매하도록 보완했습니다.
- 몬스터 HP/ATK·스킬·EXP 표·탑 적 구성·미니게임 규칙을 세이브가 덮어쓰는 경로는 없었습니다. 이 값은 원래 최신 코드에서 읽고 있으며 그대로 유지합니다.
- 로컬 JS 대부분과 CSS/이미지는 버전 없는 주소였습니다. `e7bbdd8`에서 기존 PNG 10개가 동일한 경로로 교체된 이력도 확인했습니다. 해시처럼 보이는 파일명이 현재 내용의 해시를 보장하지 않습니다. 서비스워커는 없습니다.

이는 저장 호환성 결함과 캐시 갱신 누락이 함께 있는 상태였습니다. 실제 학생 기기의 세이브와 캐시를 제공받지 않았으므로 특정 학생 증상의 단일 원인까지 단정하지 않습니다.

## 저장과 마이그레이션

- `Save.P='echo:'`, `Save.IDX='echo:__index'`, `echo:<EC코드>`, `echo:__last`는 유지합니다. 전체 초기화나 기존 슬롯 삭제는 하지 않습니다.
- 새 저장에 `saveVersion:9`와 기존 호환 표기 `v:9`를 기록합니다. 구버전은 `saveVersion`, 기존 `v`, 둘 다 없으면 0 순서로 판별합니다.
- `migrate()`는 JSON 복사본에 `SAVE_MIGRATIONS[현재 버전]`을 순서대로 적용하고, 학생 상태의 최신 기본값과 유효성을 보완합니다. 기존 루트/중첩 필드와 미등록 ID를 보존합니다. 배열을 불필요하게 덮거나 레벨/EXP를 최신 표로 재계산하지 않습니다.
- 구버전 퀴즈의 이미 받은 심화 보상을 추론하고 이전 답안 선택을 정리하는 기존 규칙은 **최신 기본값 추가 전** 실행합니다. 보상 이력은 유지합니다.
- `Save.load()`는 읽기만 합니다. `quickLoad()`가 검증된 상태로 실제 화면을 성공적으로 만든 뒤 `Save.save()`로 동일 슬롯을 최신화합니다. 지역 이동으로 진행을 보관할 때도 기존 지역의 추가 메타데이터를 유지합니다.
- 잘못된 JSON·지원하지 않는 미래 버전·슬롯 코드 불일치·마이그레이션/화면 오류는 로드를 중단합니다. 원본 슬롯은 덮지 않으며, 화면 생성 중 오류라면 시도한 루프를 중지하고 이전 화면과 좌표를 복구합니다. 학생 안내는 `저장 데이터를 불러오지 못했어요.`, 상세 내용은 `[Save]` 콘솔 로그입니다.
- 저장 공간이 부족하거나 쓰기가 불가능하면 읽기/플레이는 가능하고, 슬롯 최신화는 기존 메모리 폴백을 사용합니다. 쓰기 불가능 상태에서 새 진행을 디스크에 저장할 수 있다고 보장하지 않습니다.

보존 대상: EC 코드·이름·외형·정령·레벨·EXP·재화·아이템·보유/착용 장비·정화율·지역별 학습/전투/채집 진행·농장/씨앗/산물·생태기술·학습 답안/메모·미니게임 기록·탑 최고 층/연결된 시간/도전 이력·추가 학생 메타데이터. 사운드 설정의 `eco_mute`/`eco_volume`은 학생 슬롯과 별도로 유지합니다.

## 캐시 갱신

`js/build-version.js`의 `BUILD_VERSION`을 단일 원본으로 사용합니다. 관리 도구가 기존 정적 태그의 순서와 `defer`를 보존하면서 로컬 JS 30개·CSS 6개와 CSS의 모닥불 이미지 6개에 동일한 `?v=`를 적용합니다. 공통 이미지 사전은 첫 렌더 전 한 번 처리하고, 이후 정의되는 플로킹 사전은 정의 직후 한 번 처리합니다. 직접 생성하는 생태기술·탐험 장소·제목 이미지도 같은 버전을 사용합니다. 파일명/폴더와 CDN·외부·data/blob 주소는 유지합니다.

게임 실행에 Node.js나 빌드 과정은 필요하지 않습니다. 배포 직전 다음과 같이 관리 도구만 실행합니다.

```text
node tools/update-build-version.cjs 2026.10.08.1
```

새 HTML을 읽어야 새 주소를 사용합니다. 이미 열려 있던 페이지는 새로고침이 필요하며, 오래된 HTML만 받거나 네트워크 없이 이미 실행 중인 코드를 자동 교체하는 기능은 아닙니다. 상세 절차는 [BUILD_VERSION.md](BUILD_VERSION.md)에 있습니다.

## 다음 업데이트의 호환성 추가

1. 코드/이미지 변경은 배포 버전만 올리고 관리 도구로 주소를 일괄 갱신합니다. 게임 규칙을 세이브에 복제하지 않습니다.
2. 저장 형식 변경 시 `SAVE_VERSION`을 10으로 올리고 `SAVE_MIGRATIONS[9]=function(o){ /* 학생 데이터 변환 */ return o; }`를 추가합니다. `CURRENT_SAVE_VERSION`과 새 저장은 이를 따릅니다.
3. 기본 구조에는 학생별 진행 필드만 추가합니다. 버전 변환은 기존 값/알 수 없는 필드를 보존하고, 최신 학생 상태 검증도 새 구조에 맞춥니다.
4. 이전 버전 fixture를 유지하고 보존·중첩 누락·실패 원본 보호·새/구버전 규칙 동일 테스트를 다시 실행합니다.

## 기존 저장 위치 원칙

기존 문서의 동일 브라우저/동일 HTTP(S) origin(프로토콜·호스트·포트) 원칙은 그대로 유효합니다. 앞선 정적 파일 분리 작업에서 동일 origin의 저장 로드와 새로고침을 검증했던 기록도 유지합니다.

`file:`로 실행하던 게임과 새 `https:` 사이트의 저장은 키가 같아도 자동 이전되지 않습니다. 원래 게임 파일과 브라우저 프로필을 보관해야 하며, 프로그램 파일 백업에는 학생 기기의 플레이 기록이 포함되지 않습니다. 주소를 바꿔 데이터를 이전하려면 기존 브라우저에서 내보내기/가져오기 절차가 별도로 필요하지만, 이번 작업에서 그런 UI나 클라우드 저장은 추가하지 않았습니다.

고정 배포 후 origin과 기존 저장 키를 유지해야 합니다. 다른 기기/브라우저 사용이나 사이트 데이터 삭제는 마이그레이션으로 해결할 수 없습니다. 같은 GitHub 사용자 도메인의 다른 게임과 키가 겹칠 수는 있지만, 이번에는 기존 학생 자료의 호환성을 위해 키를 유지했습니다. 이번 query 버전은 저장소의 origin을 변경하지 않습니다.
