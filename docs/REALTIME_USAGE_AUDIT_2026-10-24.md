# Eco Chronicle Realtime 사용량 조사 보고서

조사일: 2026-10-24 · 대상: 현재 로컬 `eco-chronicle` 코드

| 사용자 제공 사용 현황 | 값 |
|---|---:|
| 지난 결제 주기 Realtime 사용량 | 5,667,208건 |
| 무료 월 한도 | 2,000,000건 |
| 한도 대비 사용량 | 약 2.83배 |
| 최대 동시 접속 | 29명 |

## 1. 결론

**주된 사용량 증가 요인은 같은 테마 전체에 전달되는 5~8Hz 위치 Broadcast다. 정상적인 동작만으로도 월 무료 한도를 초과할 수 있다.**

29명이 같은 테마에 있으면 현재도 5Hz 저부하 모드가 적용된다. 그러나 전원이 이동할 때 발신 145건/초가 수신 전달까지 포함해 약 **4,205건/초**, **252,300건/분**으로 집계된다. 5,667,208건은 이 조건에서 약 **22.5분간 전원이 이동한 규모**에 해당한다.

정지 중 위치 반복 전송이나 정상적인 지역 이동에 따른 채널 중복 누수가 주원인이라는 증거는 발견하지 못했다. 다만 비활성 탭의 채널 유지와 입장·재접속 시 위치 요청은 추가 사용량을 만들 수 있다.

**권장 기본 운영은 ‘접속인원·탑 기록 공유 + 정지된 다른 학생 캐릭터 표시’다.** 무료 한도를 우선한다면 연속 위치 동기화를 기본으로 유지하기는 어렵다.

## 2. 조사 범위와 한계

- `js/presence.js`, `js/movement.js`, `js/remote-players.js`, `js/player-list.js` 전체
- `index.html`의 로딩 순서, `js/supabase.js` 초기화, 게임의 이동·화면 전환·숨김 이벤트 관련 호출
- 기존 이동/Presence/탑 기록 검사 및 추가 메모리 모의 검증
- Supabase 공식 메시지 집계 문서

실제 Realtime 테스트 접속을 새로 만들지 않았다. 과거 사용량 세부 내역이나 실제 게시본·학생 캐시 버전까지 검증한 것은 아니다. 따라서 지난 5,667,208건의 정확한 원인별 비율은 확정하지 않는다.

**게임 코드·Supabase 설정·Cloud Save·관리자 기능·학생 저장 데이터는 변경하지 않았다. 이 문서는 조사 결과와 미반영 제안이다.**

## 3. 현재 코드 확인 결과

| 조사 항목 | 현재 동작 | 판단 |
|---|---|---|
| 위치 전송 주기 | 기본 125ms, 저부하 200ms | 이동 중 최대 약 8Hz / 5Hz |
| 인원에 따른 저부하 전환 | 원격 플레이어 25명 이상 | **총 26명부터** 5Hz. 총 25명은 기본 8Hz |
| 추가 저부하 조건 | 반복 전송 실패·지연, 프레임 성능 저하 | 전환 후 해당 페이지에서는 5Hz 유지 |
| 정지 상태 | 좌표·방향·moving이 같으면 생략 | 안정된 정지 구간에서 추가 위치 발신 0건 |
| 혼자 있는 채널 | 원격 인원 0명이어도 위치 전송 | 생략 가능 |
| Presence 검사 | 500ms마다 로컬 상태 비교 | 500ms마다 네트워크 전송하는 구조는 아님 |
| Presence track | 요약/외형 변경 또는 재접속 때 호출 | 변경 없는 상태에서 추가 track 0회 |
| 채널 구성 | 테마 채널 하나에 Presence와 Broadcast 공유 | 정상 경로에서 중복 구독 증거 없음 |
| 접속인원 UI | 상태가 달라질 때 목록 렌더링 | UI 검사 타이머 자체는 네트워크 사용 없음 |
| 원격 렌더링 | 정지 애니메이션 중단, 화면 밖 보간 생략 | 성능 최적화는 존재하지만 메시지 건수 절감과는 별개 |

전송 위치는 0.1 단위로 반올림한 좌표를 비교한다. 별도의 큰 이동 거리 기준은 없어, 좌표가 계속 바뀌면 전송 간격마다 발신할 수 있다.

### 정지 중에도 발생하는 예외

입장·재접속 직후 초기 위치, 새 멤버 입장, 방향 변경, 이동 종료, 다른 학생의 위치 요청 응답은 정지 상태에서도 발생할 수 있다.

`world-position-request`는 채널 전체에 전달되며, 받은 다른 학생들이 자신의 위치를 다시 보내도록 한다. 초기 위치가 누락된 동안 약 750ms 이상 간격으로 최대 3회 요청한다. **새 멤버 추가 시 재시도 횟수가 초기화되므로 페이지 전체에서 총 3회라는 의미는 아니다.** 입장·재접속이 몰리면 요청과 응답이 일시적으로 증가한다.

5Hz/8Hz는 위치 메시지의 상한이며 이 요청 메시지는 별도다.

## 4. 비활성화·화면 전환·퇴장 처리

| 상황 | 확인 결과 |
|---|---|
| 지역 변경 | 기존 테마 송신은 테마 검사로 차단. 약 500ms 검사 후 기존 채널 제거 및 새 채널 참가 |
| 페이지 이동/탭 종료의 pagehide | 위치 타이머 중단, 세션 분리, 채널 정리 시도 |
| 오프라인 / 수동 disable | 전송 중단 및 원격 목록 정리 |
| **탭 비활성화·화면 숨김** | **숨김을 이유로 송신과 채널 구독을 중단하는 처리가 없음** |
| 전투·미니게임·가방 | 본인 위치는 정지 상태로 수렴하지만 다른 학생 메시지의 수신 대상에는 남음 |
| 타이틀·캐릭터 생성 | 현재 조건상 Presence 참가 가능 |

비활성 탭에서는 브라우저 타이머 제한과 기존 키 해제로 이동이 줄 수 있다. 그러나 명시적으로 채널을 떠나는 것은 아니다. 모의 검증에서 숨김 상태의 좌표 변화는 계속 전송됐고, 정지 중에도 다른 학생의 위치 요청에 응답했다.

정상 지역 왕복 20회 검사에서는 활성 채널 1개가 유지됐고 이전 채널 콜백도 무시됐다. UI/상태 검사 타이머는 고정 개수이며 지역 변경마다 증가하는 구조는 발견하지 못했다. 일부 검사 타이머가 pagehide에서 별도로 정리되지 않더라도 이것이 곧 Realtime 발신을 뜻하지는 않는다.

장애 시 약 3초 후 채널을 교체하는 구조에는 애플리케이션 차원의 점진적 재접속 간격 증가가 없다. 불안정한 Wi-Fi에서 재가입·track·초기 위치 요청이 반복될 가능성은 있다. 장시간 실제 장애 상태의 채널 잔존·사용량은 이번 모의 검사만으로 보증하지 않는다.

## 5. 사용량 계산

Supabase는 Broadcast를 **발신 1건 + 수신 클라이언트당 1건**으로 집계한다. 현재 `self:false`이므로 같은 채널 N명에게서 발생한 발신 1건은 자신을 제외한 N−1명에게 전달되어 대략 N건이 된다. [공식 집계 기준](https://supabase.com/docs/guides/platform/manage-your-usage/realtime-messages)

같은 테마의 구독자 N명, 이동 중인 학생 M명, 위치 발신 주파수 f일 때:

```text
초당 위치 발신             = M × f
초당 위치 메시지 집계      ≈ N × M × f
전원 이동 시              ≈ N² × f
지역이 나뉜 경우           ≈ 각 지역의 (N × M × f)를 합산
```

### 25~30명, 40분 수업

| 같은 테마 인원 | 1명당 주파수 | 전체 발신/초 | 집계/분 | 40분 내내 이동 | 평균 30% 이동한 40분 |
|---:|---:|---:|---:|---:|---:|
| 25명 | 8Hz | 200건 | 300,000건 | 12,000,000건 | 3,600,000건 |
| 26명 | 5Hz | 130건 | 202,800건 | 8,112,000건 | 2,433,600건 |
| 29명 | 5Hz | 145건 | 252,300건 | 10,092,000건 | 3,027,600건 |
| 30명 | 5Hz | 150건 | 270,000건 | 10,800,000건 | 3,240,000건 |

29명 전원 이동 시 각 기기는 다른 28명의 위치를 최대 140건/초 받는다. 총 25명도 성능·실패 조건으로 저부하가 켜진 경우에는 표의 8Hz보다 감소한다.

이는 **위치 메시지만의 추정치**다. Presence, 초기 위치 요청, 재접속 등은 별도다. 평균 30% 이동은 학습·전투·미니게임과 필드 이동이 섞인 수업을 가정한 값이며 실측 이동률이 아니다. 최대 동시 접속 수만으로 월 총량을 확정할 수는 없다.

### 전송 주기별 월 사용량 비교

가정: 같은 테마 30명, 수업당 40분, 평균 위치 송신 활동률 30%.

| 위치 전송 간격 | 수업 1회 | 월 8회 | 월 20회 |
|---|---:|---:|---:|
| 현재 200ms | 3,240,000건 | 25,920,000건 | 64,800,000건 |
| 1초 | 648,000건 | 5,184,000건 | 12,960,000건 |
| 5초 | 129,600건 | 1,036,800건 | 2,592,000건 |
| 15초 | 43,200건 | 345,600건 | 864,000건 |
| 연속 위치 전송 없음 | 0건 | 0건 | 0건 |

마지막 행도 Presence 등의 사용량까지 0이라는 뜻은 아니다. 모든 행에서 추가 메시지는 제외했다. 이동 시작/정지/방향 변경이 전송 제한을 우회하면 예상보다 증가한다.

**1Hz로 낮추는 것만으로는 월 무료 한도를 지키기 어렵다.** 5초 간격도 월 수업 횟수와 실제 활동률에 따라 한도를 초과한다.

## 6. 권장 운영안

### 우선 권장: Presence 유지 + 정지 캐릭터 표시

- 접속인원, 닉네임, 정령, 레벨, 대표 장비, 진행 단계, 탑 기록 공유 유지
- 연속 위치 Broadcast와 초기 위치 요청은 기본 중단
- 기존 remotePlayers의 Presence 기반 생성/제거 및 임시 위치 배치를 재사용해 다른 학생 캐릭터 표시 유지
- 표시 위치는 실제 상대 좌표가 아닌 임시 배치로 구분

현재 코드에 이미 이 기반이 있어 수정 범위를 작게 잡을 수 있다. 무료 한도 우선일 때 가장 적합한 방향이다. Presence 사용량은 학생의 실제 요약 변경·입퇴장 횟수에 따라 남으므로 월 총량 보장은 별도 측정이 필요하다.

### 선택안: 낮은 빈도의 위치 표시

월 8회 안팎 수업과 평균 송신 활동률 30%를 전제로 하면 5초 간격을 검토할 수 있다. 월 20회 수준에서는 15초 정도가 더 보수적이다. 다만 이 간격에서는 현재 렌더러로 부드러운 실시간 이동을 기대하기 어렵다. 연속 움직임이 중요하면 추후 5~6명 단위 이동 채널 등 전달 대상을 줄이는 설계가 필요하다. 전체 접속인원·탑 기록 Presence는 별도로 유지할 수 있다.

## 7. 권장 조정값과 적용 우선순위

| 우선순위 | 항목 | 권장값 / 정책 |
|---:|---|---|
| 1 | 기본 위치 송신 | **0Hz, 정지 캐릭터 표시 유지** |
| 2 | 숨김 탭 | 즉시 위치 발신 중단, 30초 이상 숨김이면 채널 퇴장 |
| 3 | 참가 시점 | 학생이 실제 게임에 진입한 뒤 참가. 타이틀/생성 중에는 미참가 |
| 4 | 혼자 있는 채널 | 위치 발신 0회 |
| 5 | 초기 위치 요청 | 이동 표시 중단 시 요청도 중단. 유지할 때는 입장당 중복 요청·전원 반복 응답 축소 |
| 6 | Presence | 실제 요약 변경 시만 공유. 연속 변경은 합쳐 최소 10초 간격 권장 |
| 7 | 재접속 | SDK 복구와 중복되지 않도록 5→10→20→40→60초 대기 및 작은 무작위 지연 |
| 8 | 월 예산 | 위치에 100~120만 건 이하, 나머지는 Presence·입퇴장·재접속 등에 확보 |
| 9 | 계측 | 위치/요청 발신, track, 재접속, 활성 채널 수를 구분해 집계 |

월 예산은 운영 목표이며 구현된 강제 제한이 아니다. 실제 월 수업 횟수·활동률을 확인하고 조정해야 한다.

**효과를 혼동하면 안 되는 항목**

- Presence의 500ms 로컬 검사만 느리게 해도 네트워크가 같은 비율로 줄어드는 것은 아니다.
- 화면 밖 캐릭터 숨김, DOM 최적화, 수신 후 seq/테마 필터링은 이미 전달된 메시지 건수를 줄이지 못한다.
- payload를 작게 만드는 것은 전송량에는 유리하지만 발신·전달 횟수 자체를 줄이지는 않는다.
- 기존 `ecoMultiplayer.disable()`은 Presence까지 끄므로 접속인원·탑 기록 유지 목표에 맞는 최종 해결책이 아니다. 이동 동기화만 선택적으로 중단하는 방향이 필요하다.

## 8. 검증 결과와 다음 확인 항목

| 검증 | 결과 |
|---|---|
| 기존 이동 검사 | 통과: 발신 제한, 정지 생략, 상태 분리, 순서 검사 |
| 기존 Presence 검사 | 통과: 35명 처리, 지역 왕복 20회 후 채널 1개, 변경 없는 track 0회 |
| 기존 접속인원·탑 기록 검사 | 통과: 최고 기록 변경만 공유, 이력/도전 횟수 변경은 미공유 |
| 추가 메모리 모의 검사 | 1/25명 8Hz, 26/29/30명 5Hz 확인 |
| 정지 5초 | 추가 메시지 0건 |
| 혼자 이동 | 8회/초 발신 확인 |
| 숨김 상태 | 좌표 변화와 다른 학생의 위치 요청 응답을 차단하지 않음 |
| 실제 서비스 테스트 접속 | 새로 만들지 않음 |
| 게임/서버 변경 | 없음 |

실제 사용량의 원인별 비율을 확정하려면 동일 결제 기간의 **Broadcast Events / Presence Events / Rate of Channel Joins**를 비교한다. 사용량 화면이 조직 전체 합계인지 해당 프로젝트만 선택한 값인지도 확인한다. [Realtime 보고서 안내](https://supabase.com/docs/guides/realtime/reports)

현재 `ecoMultiplayer.getStats()`의 sent/received는 요금 집계와 같지 않다. 위치 요청 발신 수는 하위 `ecoMovement.getStats().requests`에 있고, 수신 통계는 처리된 위치 메시지 중심이므로 청구 건수 전체를 대신할 수 없다.
